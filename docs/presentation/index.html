The Problem

단일 AI 어시스턴트의 치명적 한계

하나의 거대 프롬프트나 단일 챗봇으로 풀스택 프로젝트를 개발할 때 발생하는 4대 병목

❌ 컨텍스트 오염 (Context Pollution)

기획, DB 스키마, REST API, React UI 코드가 한 대화창에 뒤섞여 토큰이 폭증하고, 이전 규칙을 망각하거나 환각(Hallucination) 발생

❌ 영역 침범 사고 (Boundary Violation)

프론트엔드 버튼 디자인을 수정해달라고 요청했더니, 백엔드 서비스 파일이나 DB 마이그레이션까지 임의로 수정하여 런타임 오류 유발

❌ 대형 파일 스파게티 코드

코드 분할 원칙 없이 한 파일에 800~1,000줄 이상의 거대 컴포넌트를 생성하여 추후 유지보수 및 디버깅 불가능

❌ 동기화 병목 (Sequential Blocking)

"백엔드 다 짤 때까지 프론트엔드는 대기"하는 직렬 방식으로 인해 AI 개발 속도가 사람보다도 지연

Core Concept

Antigravity 패러다임: Agent vs Skill

역할(Persona)과 도구(Tooling)의 명확한 분리를 통한 모듈러 아키텍처

🤖 Agent (전문가 페르소나)

  • 명확한 직무(Role): 기획자, 백엔드, 프론트엔드, API 뷰어, QA 테스터
  • 런타임 격리(Workspace): branch (독립 브랜치) vs share (동일 저장소)
  • 모델 최적화(Model): 고난도 설계엔 pro, 단순 조회/QA엔 flash 할당
  • 책임 경계(Ownership): 허용된 쓰기 디렉토리 외 수정 불가

🛠️ Skill (도구함 & 실행 절차)

  • 작업 지침서(SKILL.md): 도메인 표준 규칙 및 프롬프트 가이드
  • 자동화 스크립트(scripts/): 정적 분석기, Linter, API 검사기, QA 실행기
  • 템플릿(templates/): 사양서 템플릿, 테스트 케이스 규격서
  • 재사용성: 여러 에이전트가 필요에 따라 호출하여 실행

💡 공식: 에이전트(역할 + 권한 격리) × 스킬(실행 도구 + 자동화 검증기) = 무결점 자율 개발팀

Specialized Skills

5대 전담 스킬 (Specialized Skills) 매핑

에이전트가 호출하여 즉각적인 검증과 표준을 집행하는 재사용 스킬 묶음

📋 feature-spec-writer

사용자 인터뷰 프레임워크 및 기획 사양서 자동 검증기 (spec_validator.py)를 탑재하여 DB, API, 컴포넌트, Mock 데이터 완결성 검증

🔍 api-spec-reader

api_inspector.py CLI를 통해 문서와 실제 Express 라우트/컨트롤러 소스 코드 간 엔드포인트 및 파라미터 정합성 스캔

⚛️ react-component-developer

React 18 모듈러 컴포넌트(Sub-components), Zustand 전역 상태, Portal 팝업, safeStorage 표준 개발 지침 제공

🛡️ react-component-reviewer

정적 분석기(component_reviewer.py)를 통해 400줄 제한, Ghost State, 테마 색상 하드코딩을 기계적으로 차단

🧪 scenario-qa-runner

Positive/Negative 시나리오를 바탕으로 풀스택 회귀 테스트를 자동 실행(qa_runner.py)하고 에러 핸들링 및 정합성 검증

Phase 0 & 1

계약 기반 기획 & Zero-Blocking 병렬 개발

"코드를 작성하기 전에 완벽한 인터페이스 계약을 먼저 체결한다"

📝 사양서 필수 4대 계약 요소

  • Prisma DB 모델: 모델명, 필드 타입, 관계, 인덱스 사전 정의
  • REST API 명세: HTTP Method, 엔드포인트 URL, Req/Res DTO, 상태 코드 매트릭스
  • UI 컴포넌트 트리: 400줄 이하 파일 분할 설계 및 상태 스토어 계획
  • MOCK DATA 계약: 프론트엔드가 즉시 바인딩 가능한 완전한 더미 데이터셋

⚡ Zero-Blocking 병렬 착수 원리

  • 프론트엔드의 독립성: 백엔드가 데이터베이스를 구축하는 동안 프론트는 사양서의 Mock Data로 UI 화면을 100% 선행 개발
  • 브랜치 격리(Branch Workspace): 서로 다른 독립된 Git 워크스페이스에서 개발하므로 코드 충돌(Merge Conflict) 제로
  • 단위 테스트 선행: 백엔드는 비즈니스 로직마다 Vitest 성공/실패 단위 테스트 동시 구축
Phase 2 & 3

브릿지 인계와 기계적 품질 게이트 (Quality Gates)

사람의 주관이 아닌, 스크립트 기반의 엄격한 Exit Criteria

Case Study 2

실전 사례: 복합 채팅 알림 고정 버그 추적 및 복구

"실시간 채팅 알림 2개가 안 꺼져요" ➔ 풀스택 원인 분석 및 완벽 복구

🔍 정밀 원인 분석

  • 정체: 과거 자동 테스트 채널 2개(ui-audit-channel-*)에 미확인 검증 메시지 잔여

  • DB 정리: 잔여 테스트 채널 삭제 ➔ unreadCount = 0 정상화
  • UI 필터 보완: GLOBAL || GENERAL 채널 모두 정상 렌더링
  • 백엔드 API 신설: POST /api/chat/read-all 및 Vitest 단위 테스트 Pass
  • 실시간 동기화: TanStack Query 캐시 무효화 및 웹소켓 연동
  • 편의성: 채널 헤더에 [모두 읽음] 버튼 신설
Best Practices

에이전트 & 스킬 구축 핵심 노하우 (Key Takeaways)

다른 팀에 멀티 에이전트를 도입할 때 반드시 지켜야 할 4대 원칙

1. 규칙을 말로 쓰지 말고, 스크립트(Linter)로 만들어라

"400줄 넘기지 마세요", "테마 변수 쓰세요"라는 프롬프트는 AI가 쉽게 잊어버립니다. component_reviewer.py처럼 기계적으로 검사하여 0 error일 때만 통과되도록 파이프라인에 강제하세요.

2. 에이전트 파일에 '금지 사항(Forbidden)'을 명시하라

백엔드 에이전트에게 "프론트 파일 수정 절대 금지"를 적어두지 않으면, 편의상 프론트 코드를 임의 수정하여 협업 브랜치가 충돌합니다. 역할 경계(Boundary)를 철저히 격리하세요.

3. 파일 인코딩(BOM)과 테마 토큰을 엄수하라

Windows 환경의 한글 깨짐을 방지하기 위해 UTF-8 with BOM을 자동 적용하고, 인라인 색상 하드코딩을 금지하여 다크/라이트 테마 호환성을 기계적으로 유지하세요.

4. Mock Data 계약서가 병렬 개발의 치트키다

사양서에 완성된 더미 데이터를 사전에 합의해 두면, 프론트엔드가 백엔드 API 완료를 기다릴 필요가 전혀 없어집니다. 개발 속도가 2~3배 빨라집니다.

Adoption Roadmap

내 프로젝트에 도입하는 3단계 로드맵

복잡한 도구 없이도 당장 오늘부터 시작할 수 있는 점진적 도입 전략

STEP 1

아키텍처 규칙 정의

GEMINI.md 또는 AGENTS.md에 기술 스택, 레이어 분리 원칙, 파일 크기 제한, 금지 사항을 명문화합니다.

STEP 2

검증 스킬(Scripts) 패키징

.agents/skills/ 폴더를 만들고, 기획 검증기(spec_validator)나 코드 정적 분석기(reviewer) 스크립트를 작성합니다.

STEP 3

에이전트 역할 분할

.agents/agents/에 기획, 백엔드, 프론트, QA 에이전트를 선언하고 브랜치 워크스페이스 격리와 모델 티어를 할당합니다.
